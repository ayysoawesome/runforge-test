# Правила проекта

Проект использует React, TypeScript, Vite, Tailwind CSS и Feature-Sliced Design (FSD). Следуй существующим соглашениям и меняй только то, что нужно для задачи.

## Архитектура

- Организуй код по FSD: `app` для инициализации приложения, `pages` для страниц, `widgets` для крупных блоков, `features` для пользовательских действий, `entities` для предметных сущностей, `shared` для переиспользуемой инфраструктуры и UI. Создавай слой или слайс только при реальной необходимости.
- Соблюдай направление зависимостей: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Нижний слой не импортирует верхний. Слайсы одного слоя не зависят друг от друга; общую логику выноси на подходящий нижний слой.
- Публичный API слайса размещай в его `index.ts`. При импорте из другого слайса или слоя используй этот API, без обращения к внутренним файлам. Внутри слайса допустимы прямые относительные импорты.
- Экспортируй из `index.ts` только то, что действительно нужно снаружи; предпочитай явные реэкспорты вместо `export *`.

## Принципы разработки

- **KISS:** выбирай самое простое решение, которое решает текущую задачу.
- **DRY:** устраняй дублирование знаний и правил; не создавай абстракцию только из-за внешне похожих строк кода.
- **YAGNI:** не добавляй функциональность, конфигурацию и расширяемость без текущей потребности.
- **BDUF (Big Design Up Front):** не проектируй большую систему наперёд. Уточняй архитектуру по мере появления требований, сохраняя ясные границы FSD.
- **SOLID:** поддерживай понятные ответственности и зависимости, применяя принципы там, где они упрощают изменение кода; не усложняй небольшие компоненты ради формального соответствия.
- **APO (Avoid Premature Optimization):** сначала обеспечь корректность и читаемость; оптимизируй после выявления конкретной проблемы или измерения.

## Код и стили

- Используй только именованные экспорты; `export default` не применяй. React-компоненты объявляй в форме `export const ComponentName = (...) => { ... }` и реэкспортируй через `index.ts`, если они нужны за пределами слайса.
- Для новых стилей используй utility-классы Tailwind CSS. Глобальный CSS оставляй для подключения Tailwind, токенов темы и действительно глобальных правил. Не добавляй отдельный CSS-файл для компонента, если задача решается классами Tailwind.
- Соблюдай строгую типизацию: не используй `any`, оператор приведения типов `as` и другие способы обхода проверки типов. Для неизвестных данных используй `unknown` и сужай тип проверками; типы на границах модулей и API объявляй явно.
- Состояние размещай как можно ближе к месту использования, а серверные запросы и их кэширование отделяй от представления.
- Сохраняй принятый в проекте стиль импортов и форматирования. Не меняй несвязанные файлы и не добавляй зависимости без необходимости.

## Проверка

- После изменения кода запускай `pnpm build` и `pnpm lint`, если они применимы к задаче. Исправляй ошибки, вызванные своими изменениями.
- Для вопросов о синтаксисе, настройке, миграции или поведении библиотек, фреймворков, SDK, API, CLI и облачных сервисов сначала получай актуальную документацию через Context7 MCP (`resolve-library-id`, затем `query-docs`). Для обычного рефакторинга и логики приложения это не требуется.

## Коммиты

- Заголовок коммита оформляй как `<type>(<scope>): <сообщение>`, например `feat(runs): добавить список запусков`.
- Выбирай подходящий тип: `feat`, `fix`, `style`, `chore`, `refactor`, `docs`, `test`, `perf`, `build` или `ci`. `scope` указывает на затронутый слайс или область проекта и обязателен.
- Сообщение в заголовке и пункты тела коммита пиши на русском языке; служебные `type` и `scope` оставляй в формате выше.
- После заголовка оставляй пустую строку. В теле коммита перечисляй по пунктам, что было сделано; каждый пункт начинай с `- `.
